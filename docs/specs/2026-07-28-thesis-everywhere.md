# 所有个股页都要有「投资逻辑」模块

> sway：`/entity/<三一重工>` 有投资逻辑模块，`/entity/<万向钱潮>` 没有。要所有的都有。

## 根因不是 bug，是覆盖率

实测：5498 家 COMPANY 里只有 **166 家**有 `Thesis`（**3.0%**），5251 家缺（且都有新闻）。
三一重工在那 166 家里，万向钱潮不在。

而 `entity/[id]/page.tsx` 的 `thesisBlock` 在没有 thesis 时是 `null`——**模块整个消失**。
所以用户看到的是「有的页有、有的页没有」，会以为这只股不支持，而真实原因只是还没轮到它。

原有回填 `backfill-thesis.ts` 每轮 8 家、cron 每 150 分钟一轮 ≈ 77 家/天，补完 5251 家要 **68 天**。

## 三件事

### 1. 模块永不消失

没有 thesis 时不再返回 `null`，改渲染 `ThesisPending` 占位卡（骨架 + 「正在生成」）。
只对 COMPANY / STOCK 渲染——板块和人物没有「投资逻辑框架」这回事。

### 2. 打开即生成（按需）

`ThesisPending` 挂载时触发 `entity.ensureThesis` mutation，生成完 `router.refresh()` 换上真卡。

**为什么不在服务端直接生成**：一次实测 ~16s，挂在 SSR 上会把整页拖死
（与「外部第三方接口拆到 Suspense」同一条教训）。

`server/thesis-ensure.ts` 负责幂等 + **单飞**：
- 先查库，已有直接返回
- 进程内以 entityId 为键合并并发请求——多个用户同时打开同一页只烧一次 token
- `upsert` 入库，跑一半被杀也不会写坏
- **绝不抛**：它挂在页面链路旁边，AI 抽风不该让整页出错；失败打日志（不裸 catch）并给「重试一次」

「有人打开」本身就是最好的优先级信号——比任何预排序都准。

### 3. 后台全量回填

`src/scripts/backfill-all-thesis.ts`，一次跑完而不是两个月：
- **幂等**：已有的跳过，被杀了原样重跑即续
- **单跑**：只起这一个后台任务（并发跑多个长回填会被系统回收——踩过）
- **按需重排**：`ORDER BY 被自选数 DESC, 关联新闻数 DESC`，最可能被打开的先补
- 固定并发池（默认 6，实跑用 8），每 25 家打一次进度 + ETA

实测：并发 3 时 ~37s/家（单发是 16.5s，并发下变慢）。5300 家按并发 8 估算数小时量级。
成本：每份约 3600 token，deepseek 下总计几美元。

## 验收

- `/entity/<一博科技>`（跑之前确认库里无 thesis）→ 打开页面，**8 秒后库里已生成**（5 个维度），
  再次请求页面 HTML 里「正在生成」0 处、真卡内容 2 处
- 万向钱潮对照页同样有了
- 846 测通过 / `tsc` 新文件零错误 / `next lint` 0 error / build exit 0 / `start-prod.sh` 重启

## 注意

`backfill-all-thesis.ts` 失败计数不当作整体失败——AI 偶发返回不合规 JSON 是常态，
下次重跑会自动重试（幂等）。判「完成」看「仍缺 N 家」这个数，不看 exit code。

## 回填被系统杀掉（2026-07-28 实际发生）

一次性跑全量（5327 家、并发 8、ETA 200 分钟）在 **950 家 / 约 36 分钟**时被系统回收——
和「并发跑多个长时后台回填会被系统杀」是同一类问题，这次连**单跑**都会被杀，只要够长。

但**进度全部保住**：幂等设计让已生成的不会丢，覆盖率从 3.0% → **20.7%**（166 → 1140 家）。

改法：**有界分片 + cron 托管**，不再一次性跑全量。
新增临时 cron「解牛 投资逻辑全量补齐(临时·补完即删)」每 45 分钟跑一片
（`--limit=600 --concurrency=8`，一片约 23 分钟，留足余量不撞下一轮）。
补齐后在 `/cron` 页删掉这条。

一般原则：**长回填不要靠「一次跑完」，要靠「每片都能独立完成 + 幂等 + 有人替你重跑」**。
cron 恰好提供后两者。
